# 《山海拾遗录》作品集投递说明

本文档用于投递简历、准备面试和整理作品集页面。完整设计事实仍以 `docs/GDD-山海拾遗录.md` 为准；这里保留招聘方最容易快速理解的版本。

## 一句话介绍

《山海拾遗录》是一款基于《山海经》的 Godot 单机 Roguelike 卡牌探索原型，包含五章地图探索、实时遭遇、卡牌战斗、图鉴学习、多角色构筑、存档和三档终局。

## 投递时推荐展示顺序

1. **30 秒口头介绍**：说明类型、核心循环、个人职责和当前完成度。
2. **2-3 分钟视频**：让招聘方快速看到可运行内容。
3. **README / 作品集页**：展示系统清单、数据规模、测试覆盖和技术栈。
4. **GDD 节选 PDF**：只放核心设计，不直接投 100 页以上的完整 GDD。
5. **可执行 Demo 包**：作为加分项，不要求对方必须装 Godot。

## 2-3 分钟演示视频脚本

| 时间 | 画面 | 重点 |
| --- | --- | --- |
| 0:00-0:20 | 主菜单、角色/图鉴统计、教程/设置入口 | 说明项目是完整可运行原型，不是单场景 demo |
| 0:20-0:45 | 进入地图，展示顶距/等距探索、小地图、章节标题 | 展示 Roguelike 探索和章节推进 |
| 0:45-1:20 | 触发普通敌人或精英/Boss，进入卡牌战斗 | 展示卡牌、能量、状态、敌人意图和奖励 |
| 1:20-1:45 | 打开事件/商店/宝箱/驿站之一 | 展示地图节点与资源选择 |
| 1:45-2:10 | 打开图鉴详情 | 展示文化文本、原文/译注/现代关联 |
| 2:10-2:40 | 通过开发跳关或存档进入终局/书房 | 展示结局收藏、长线进度和闭环 |

视频录制原则：不要解释过多规则，优先让画面证明系统已经连起来。出现开发工具时需要说明是为了演示快进，公开 Demo 会隐藏。

## GDD 节选 PDF 建议

完整 GDD 可以保留为仓库文档，但投递时建议导出 8-15 页节选版：

1. 项目定位与一句话立意
2. 核心循环图
3. 地图探索规则
4. 卡牌战斗规则
5. 三流派关键词与角色构筑
6. 图鉴学习与文化表达
7. 章节结构与终局条件
8. 当前完成度矩阵
9. 后续版本路线
10. 测试与验收标准

不要把完整历史版本记录放进节选版；它对面试官价值低，会稀释重点。

## 简历描述模板

### 游戏策划 / 系统策划方向

- 独立设计并实现《山海拾遗录》Godot Roguelike 卡牌探索原型，完成五章地图探索、卡牌战斗、图鉴学习、多角色构筑和三档终局闭环。
- 设计 92 张卡牌、40 个敌人、40 个事件和 132 条图鉴条目的数据结构与内容规则，并维护 GDD 完成度矩阵、验收标准和后续版本路线。
- 将《山海经》原文、白话译注和玩法机制结合，通过“唤醒而非消灭”的主题统一战斗、图鉴、事件和终局表达。

### Godot / 客户端开发方向

- 使用 Godot 4.3 / GDScript 搭建单机 Roguelike 卡牌游戏原型，实现地图探索、卡牌战斗、状态系统、存档、设置、图鉴和终局场景。
- 采用 JSON 数据驱动卡牌、敌人和事件内容，接入 smoke 回归脚本覆盖数据库加载、战斗流程、图鉴、角色、终局和外测入口。
- 处理主菜单、教程、设置、地图、战斗、书房和终局等多场景路由，支持旧存档兼容、开发入口隐藏和 Playtest 可交付检查。

## 面试时可强调的问题

- 如何把“文化传承”落到卡牌、图鉴、事件和终局，而不是只停留在美术题材。
- 为什么 v0.14 选择先做 GDD/作品集收束，而不是继续堆更多卡牌和敌人。
- 如何用 GDD 完成度矩阵区分“已实现”“已规格化”“后置完整版”。
- 如何用 smoke 脚本降低每次扩内容后的回归成本。

## 投递前检查清单

- README 第一屏能在 30 秒内说明游戏类型、完成度和个人职责。
- 视频能在 3 分钟内展示从主菜单到终局的主要闭环。
- GDD 节选版没有过多历史版本流水账。
- Demo 包或运行说明能让非开发者启动。
- 简历 bullet 写清楚“我负责了什么”，而不是只写“做了一个游戏”。
